# ArtworkPlus — Gate System Fibel (conventions & rulebook)

**Purpose of this file:** not a reference to read once — a **form that MUST be actively filled in and ticked off** before anything in the dependency tree (`EP_TREE`, `configPage.html`) is changed for any tab. Every new bug, every newly discovered inconsistency is added here as an entry — this file grows with the project, it is never "finished".

**Standing instruction for every maintainer, every time this file is read or extended:** actively look for contradictions between the rules written here, not only between a rule and the code. The user can be wrong — say so explicitly, never "repair" silently.

**Workflow rule (Session 81, corrected by the user repeatedly): for every non-trivial structural change, FIRST show the understanding/the plan and explicitly wait for a GO — NEVER implement in the same breath.** A proposal ending in "does that fit?" followed by immediately starting does NOT count as waiting for approval, even though technically a question was asked. Only when the user visibly agrees ("ja", "passt", "leg los", …) may implementation begin. This happened several times (e.g. Session 76: "was korrigierst du? erst mit mir besprechen") and is recorded here as binding so it does not happen again.

**Numbering note (Session 111 cleanup):** rules 11–18 had been assigned twice (once in Sessions 28–36, again in Sessions 93–109). The code comments and test scripts use the original numbering (e.g. "rule 14" = one grey level). The later duplicates were renumbered 19–26; every reference in the curriculum and the concept document was updated accordingly.

## Part A — The invariant ground rules

Each of these rules was earned the hard way over several sessions, every single one after a real bug found in operation. They are the reason this document exists.

0. **General-tab root switches (the root gate of a tab, e.g. `CustomPosterEnabled`, `CaseModEnabled`, `CharacterartEnabled`, `AnimatedPosterTabEnabled`, `RedCarpetEnabled`, `BackdropsTabEnabled`, `ExtraposterTabEnabled`) change EXCLUSIVELY through a direct click there — never as an automatic consequence of anything inside their own tab, whatever the combination.** This rule was established **three times independently**, in three different sessions, after three different real regressions (earliest: Session 10, "Unified Gate system" concept; again after a deadlock: "General-tab whole-tab locking - REWRITTEN"; a third time explicitly as fix #1 in "Two independent, explicitly user-corrected fixes" in the curriculum) — each time word for word: automatically switching off the tab root switch, combined with tab locking, creates an inescapable deadlock. **Consequence for the Session 29/30/34 mutation chain:** the Show-on→Enable mutation may ONLY target a real sub-feature Enable that is distinguishable from the tab root (Postercase/Keyart/Extraposter/Extrakeyart/Backdrops) — never `CharacterartEnabled`/`RedCarpetEnabled`, because these ARE the tab root gate themselves, no separate sub-Enable exists. Not a formality, but the same triply confirmed deadlock class.
1. **Greying flows downwards only** (parent → child), never upwards, never sideways, never onto itself. *Exception, deliberate and documented: see contradiction W1 below.*
2. **Greying never changes a stored value.** No checkbox is ticked or unticked automatically because something else got greyed. (Earlier value mutations such as Format→Enable, ShowOn→Enable were removed for exactly this reason, Session 22. *Deliberately re-introduced in a narrow, documented form since Session 29 — see Part B2.*)
3. **`target` (really disables fields) must NEVER physically contain one of the node's own `when` condition checkboxes.** That is the deadlock bug from Session 25 — mechanically checked by `test_tree_self_containment.py`, which must be green BEFORE every delivery.

    3b. **Clarification from the counter-audit (Session 27):** a node's target may well contain the trigger checkbox of ANOTHER (foreign, not its own) node — that is NOT a deadlock as long as this foreign node is a **descendant in the same cascade** and its own way back (the condition that re-activates the greying node itself) lies **outside** the greyed area. Example: Case greys `CaseModOpenCaseOnClickRow` completely when Show-on is empty — that row contains `CaseModOpenCaseOnClickEnabled`, the trigger of a sibling node. No deadlock: the way back is re-checking "Show on", which lies outside that row. **The difference to rule 3:** rule 3 forbids a node blocking ITS OWN way back. Rule 3b allows it to block a descendant's way back as long as its OWN way back (not the descendant's) stays untouched. Checked by `diagnostic_cross_node_check.py` — 13 cases found, each individually confirmed safe (Case, Postercase, Keyart, Extraposter, Extrakeyart, Characterart).

    3c. **Second, independent safe special case (Session 76, Backdrops traversal feature):** a node with `when: []` (unconditionally always active, typical for `structural: true` select wrappers per rule 13) NEVER greys its target — so its target physically never holds a real deadlock risk, whatever foreign trigger it contains, even if the foreign node is not a descendant but a pure SIBLING (rule 3b strictly does not apply, there is no descendant relationship). Example: Genre/Tag/Favorites' `*_sort` node (`when: []`) has the SortModeRow in its `target`, which itself physically contains the trigger of the `*_traversal` sibling node (`ValueIn(...SortMode...)`). Verified live: the SortModeRow is `disabled=false` in EVERY state — the `_sort` node never greys it, so it can never block. Found by `diagnostic_cross_node_check.py`; already present in the real plugin (not introduced by Session 76), never documented as safe before.

    3d. **Extension of 3c once `_sort` itself can grey again (Session 76, Favorites General/Individual):** after `_sort` (e.g. `backdropsfavorites_movies_sort`) received a REAL `when` condition (`ValueIn('BackdropsFavoritesManageMode', ['Individual'])` instead of `when: []`), 3c's original reasoning ("never greys") no longer applies literally. Still safe, for a DIFFERENT reason: `_sort` and its sibling `_traversal` share exactly the same PRIMARY condition (both check `ManageMode` first). As soon as `_sort` greys its target (the SortModeRow containing `_traversal`'s trigger), `_traversal` is NECESSARILY already greyed by the SAME condition — no state ever arises in which Traversal stays blocked because of an unreachable Sort value while Sort itself is locked for a DIFFERENT reason. Verified live (General: both locked; Individual: Sort always freely changeable, Traversal reacts live to every Sort change). **Generalized rule:** a sibling cross-node case is safe if either (a) the greying node has `when: []` (3c), OR (b) both nodes share the same primary condition as the FIRST entry of their own `when` list, so the greying node never greys its target without the dependent sibling already being grey for exactly the same reason.
4. **`headerTarget` (only dims a heading) is always safe** and may reference the very collapse in which its own trigger lives — it never disables anything, so it can never block.
5. **`headerTarget` is ALWAYS applied unconditionally**, never skipped — not even by the doubling protection (rule 6). Costs nothing, prevents nothing, must always show the correct state.
6. **A node skips its own `target` application ONLY when a real DOM check (`.contains()`) at runtime confirms** that its own target already lies nested inside a currently inactive ancestor target — NEVER assumed wholesale. A blind "parent inactive → skip child" would have silenced greying on 35 of 96 nodes in Session 26 (e.g. Case: "Show on" and "Case type" are sibling rows, no nesting).
7. **`structural: true`** marks peripheral settings (e.g. a priority selection row) that do NOT count as a "real sub-function" when checking whether a whole tab is ineffective.
8. Three condition building blocks, no more: `AllChecked` (all must be on — typical for an own Enable switch), `AnyChecked` (at least one — typical for format checkbox groups and Show-on groups), `ValueIn` (dropdown/select value). A fourth type (continuous numeric comparison, e.g. Align `>0`) was deliberately NOT introduced — it stays an own, separate function outside the tree (`epUpdateAlignRowState`).
9. External state sources (browser detection, Jellyfin host settings) are NEVER disguised as a tree condition — own, separate layer (`epUpdateBackdropsBrowserState`), applied afterwards at the end of every recompute.
10. When a collapse body contains **nothing but its own trigger element** (e.g. Genre/Studio/Tag Backdrops, only the Enable checkbox inside): **`headerTarget` only, no `target` at all** — there is nothing safe that could be disabled separately.
11. **Opacity doubling is checked PER ELEMENT, not per channel.** The original thought "headerTarget can never double because it is purely cosmetic" was wrong — CSS opacity doubles on EVERY nesting of two elements with the same class, regardless of whether fields get disabled at the same time. `epShouldSkipEl()` now checks that individually for every single element (header, body, row) at runtime — never excluded wholesale by channel.
12. **`terminal: true`** marks a node whose own activity already means "real effect" — its own children are pure refinements (e.g. a NamingMode-dependent FolderName field), not co-requirements. Without this flag the tab-button ineffectiveness function ALWAYS recurses down to the leaves — wrong for pure refinement children (example: `postercase_movies` should count as active through `PostercaseShowOnMovies` alone, not additionally require `postercase_movies_folder`'s own ValueIn condition).
13. **Position/ScaleMode nodes are ALWAYS `structural: true`.** A `<select>` always has exactly one valid value — a `ValueIn` condition on it is structurally never "off", it always fakes the "does this tab do anything at all" check (`epSubtreeEverActive`) as active, regardless of the real Show-on/Enable state. Applies to `epMakePositionNode` and its two ScaleMode children, without exception.
14. **The whole admin menu has exactly ONE grey level — never additive/nested.** For every DOM element: at any time at most ONE element in its own ancestor-or-self chain may carry the `epFieldDisabled` class — never two at once. Not an optimization but an absolute invariant (reason: Session 28, CSS opacity doubles on every nesting, 0.35×0.35 ≈ 0.12, visibly darker than anywhere else). Mechanically checked by `test_single_grey_level.py` — must be green before every delivery, just like the self-containment check. **Explicitly also applies to every hand-written single-disable function outside `epSetRowDisabled`/EP_TREE** (e.g. for buttons, which the shared function never disables automatically, see Session 76/Wipe-cache button) — not only to `epUpdateDelayDependency`/Align and the core functions. The ancestor check is always the same: ALWAYS set `.disabled` (or the real locking property) correctly (does not compound visually), the `epFieldDisabled` class only when no ancestor already carries it.
15. **Every field that functionally belongs to a position MUST also be listed as `target` in the position node itself — no exception, not even for fields with an additional, separate condition (such as Align/Max\*).** A separate extra condition may only ADDITIONALLY restrict the position dependency, never replace it. This must be checked for EVERY field individually (`epGetFieldValue`/`.disabled` directly, not just the row class), not just for the "obvious" fields like Height/Width.

    15b. **A control that sits in the same row container as an action button places the button right-aligned via `justify-content:space-between` — never with a fixed `gap` right next to it.** Established pattern: the API-key row (`Test API Key` button). Applies to every new row with control + action, without exception (Session 76, user finding: the Wipe-cache button was glued to the Source dropdown with `gap:8px` instead of being right-aligned).
16. **When testing this page outside real Jellyfin: the `pageshow` event must be fired manually on `#ArtworkPlusConfigPage` (not `window`), or simulated with a "Restore all" click — otherwise the tree computation never starts automatically, and that looks like a bug although there is none.**
17. For "make X consistent everywhere" never only walk through the tabs that look structurally alike — instead search for the underlying PATTERN automatically (here: compare every ShowOn group against every tab root gate), so structural deviations (a sub-Enable sitting elsewhere in the tab) do not prevent finding them (Session 34, Case was missed).
18. **Every side function outside the tree that changes visible/usable state MUST be called once unconditionally inside `epRecomputeDependencyTree()` itself — never only through an event listener.** A pure listener call shows the wrong state on every fresh load of a real, saved configuration until the user clicks something. New functions of this kind belong centrally in this one function, not spread over the individual call sites (restore per tab, restore all, import, pageshow) — exactly that would be forgotten again next time.
19. **Every sub-collapse below an outer FEATURE level (not directly below the tab root) gets the CSS class `epCollapseNested` on BOTH header AND body** — purely visual (indentation), shows the nesting depth. Applies e.g. to Movies/TvShows under Postercase/Keyart/Extraposter/Extrakeyart/Animated Poster/Animated Keyart (one outer feature level in between each). Does NOT apply to Characterart (only a single feature in the tab, no outer feature level — Movies/TvShows sit directly below the tab root, correctly without indentation). **This rule was forgotten THREE times** (first discovered at Postercase/Keyart/Extraposter/Extrakeyart, Session 76; then added for Favorites' 11 subs, Session 78/81; then forgotten again in the complete Animated Poster restructure, Session 90/93) — no diagnostic script checked it automatically, only "looks right when viewed" was assumed. Since Session 93: `diagnostic_nested_collapse_check.py` runs with the suite, built for exactly this. **Session 123: a SECOND step exists** — "Detail page"/"Library views" inside Movies/TV shows of Extraposter/Extrakeyart carry `epCollapseNested` AND `epCollapseNested2` (another 10 px). The diagnostic now decides by DOM depth (number of enclosing `.epCollapseBody`): 0 = no class (tab level, Characterart's own Movies/TV shows), 1 = `epCollapseNested` only, ≥ 2 = both.
20. **Every standalone, browser-openable preview copy of the real `configPage.html` (not the file itself!) needs TWO fixes, both already forgotten once:**
    - **ApiClient/Dashboard stub** (otherwise the page does not load at all — no real server present)
    - **`html { background-color: #101010 }`** (otherwise a white frame at the top — Jellyfin's real `theme.css` with this rule is never loaded outside a real server). **First found and fixed in the old Backdrops sandbox (Session 75); forgotten again in the NEW preview copy based on the real `configPage.html` (Session 90+), added in Session 94.** Since then: **always** use `build_preview.py`, never rebuild the stub by hand — the script carries both fixes built in. Buttons/checkboxes deliberately stay plain in this preview (no full Jellyfin custom-element framework loaded) — a known, accepted limitation, not a bug.
21. **In every restructure that replaces an existing single checkbox by a NEW checkbox elsewhere with the SAME id/name** (e.g. a feature-level "Show on" multi-checkbox replacing a previously per-sub single "Show on" checkbox): **explicitly remove the OLD row, do not just add the new one.** An overlooked old row creates two DOM elements with the same ID — `getElementById()` always returns only the first, while visible interaction often happens with the second, which looks like a "does not come back on" bug (Session 95, Animated Poster restructure from Session 90 affected). `diagnostic_duplicate_id_check.py` runs after every larger restructure.
22. **The generic `change` listener wiring does NOT attach to every EP_FIELDS field — only to fields that appear somewhere in EP_TREE as a real condition (`when`: ValueIn/AllChecked/AnyChecked).** A standalone post-process function outside the tree (like `epUpdateAlignRowState` or `epApplyFavoritesPeopleFormatException`, Session 102) that reads a field which appears ONLY as `target` (never as a `when` condition) gets **no** automatic listener — a change to that field then NEVER triggers a recompute, the function stays "frozen" on its last state without any syntax or runtime error. **For every field that a standalone function reads but which itself serves nowhere as a condition, an explicit `change` listener must be added** that calls `epRecomputeDependencyTree` — do not rely on the generic wiring. Found with the format exception for Favorites' People sub (Session 102): `BackdropsFavoritesPeopleSourceMode` was referenced only as the target of a `when: []` node, never as a condition, so the listener was missing entirely.
23. **When rebuilding a standalone post-process function (outside EP_TREE) that is known from an earlier session but documented only as a short description: ALWAYS read the actual, earlier implementation (curriculum entry with code, or version history) first, never re-derive it from the short description.** A first version derived from the description "adds itself on top when format is empty AND Source≠Wallpapers.com" (Session 105, `epUpdatePeopleBackdropsFormatDependency`) would have disabled the WHOLE `DependentFields` including the Source dropdown itself — a real deadlock, since the user could never switch back to Wallpapers.com to fix the state. The real version greys only the individual affected rows and always leaves the control element (here: the Source dropdown) through which the user can change the condition untouched — this detail was not in the short description, only in the actual code. Same lesson as rule 3 (no node may block its own way back), but here not caught automatically by the declarative tree check because the function deliberately lives OUTSIDE the tree — `test_tree_self_containment.py` does not cover it.
24. **Every exception function that partly takes back an existing greying set by the tree must handle the COMPLETE ancestor chain of the affected elements, not just the elements themselves.** CSS `opacity` (the basis of the `epFieldDisabled` class) is inherited from a container to ALL child elements regardless of whether the children carry the class themselves — an element with `disabled: false` and no own `epFieldDisabled` class still looks dimmed when an ANCESTOR (e.g. the `DependentFields` container itself) still carries the class. **Before ticking off such an exception as "done": walk the complete `parentElement` chain of the affected element up to the tab root and check EVERY level for the class** (not just the element itself) — plain `.disabled`/`classList` single checks are not enough, a screenshot comparison reveals it more reliably. Found after three consecutive, each only partially corrected attempts (Sessions 102/106/107 each handled one level only — People's own fields, the outer header, the shared timing fields — never the `BackdropsFavoritesDependentFields` container itself), fully uncovered only in Session 108 by a screenshot comparison.

    **Concrete reference instead of re-deriving it every time (user request, Session 109) — the actual cascade for Favorites Backdrops, so future work can look it up instead of re-discovering it:**

    | Level | Element(s) | Set by |
    |---|---|---|
    | 1 | `BackdropsFavoritesDependentFields` (container) | Root node `backdropsfavorites` itself: own class + `.disabled=true` on ALL descendant inputs when `AnyChecked(BdFormat_*)` AND `AllChecked(BackdropsFavoritesEnabled)` are not both satisfied |
    | 2 | Outer header `[data-collapse="backdropsFavorites"]` | Root node itself (`headerTarget`) |
    | 3a | Shared fields directly in the container: `BackdropsFavoritesCycleTimeMs`, `...KenBurnsEnabled`, `...KenBurnsZoomMs`, `...KenBurnsPanMs` (no own row ID for the first two) | Level 1's `.disabled` cascade (no own node) |
    | 3b | Manage/Order/Traversal (`BackdropsFavoritesManageMode` etc.) | Level 1's cascade + own `structural` nodes (ManageMode-dependent). Since Session 116 the 10 sub HEADER nodes depend on their Enable only — Manage=General greys just the sub's Sort/Traversal rows, never the header |
    | 3c | **Shared fields IRRELEVANT for People** (`BackdropsFavoritesMainOnly`/`...ManageMode`/`...GeneralSortMode`/`...GeneralTraversalMode` — pure pool-sorting concepts for the other 10 subs): rightly stay `.disabled=true`, but STILL need their own `epFieldDisabled` class (via `.closest('.epRow')`, since some have no own row ID) — otherwise only inconsistent NATIVE browser looks (select slightly dimmed via `:disabled`, the label next to it stays fully bright).     **For a complete exception (People free, everything else stays locked) ALL SIX levels (incl. 3c) must be handled individually:** level 1 (remove the container class), level 2 (outer header, own function `epUpdateFavoritesHeaderFormatException`), levels 3a+5 (reset `.disabled` + unlock own rows/headers), level 3c (explicitly dim the fields irrelevant for People, do not just leave `.disabled`), level 4 (give the 10 other subs the class explicitly themselves, since they no longer dim automatically after level 1 is removed). See `epApplyFavoritesPeopleFormatException`/`epUpdateFavoritesHeaderFormatException` in `configPage.html` for the complete, now correct implementation.
25. **A field that correctly stays `.disabled=true` does NOT look correctly dimmed by that ALONE.** The native browser default for `<select disabled>`/`<input disabled>` (Chrome: `opacity: 0.7` on the element itself) affects only the field, never its `<label>` — without the own `epFieldDisabled` class on the whole row the label stays fully bright while the field is slightly (natively, not our 0.35) dimmed. Visibly "half dimmed", inconsistent with the rest of the menu. **Every time an exception function unlocks a container (rule 24), it must also explicitly set the `epFieldDisabled` class on the own row of fields INSIDE that container that should correctly stay locked** — not just leave `.disabled` untouched and rely on the (now removed) container inheritance. Found at Favorites' `BackdropsFavoritesMainOnly`/`ManageMode`/`GeneralSortMode`/`GeneralTraversalMode` (Session 109) — overlooked in the first version of the rule-24 fix (Session 108) because only "what must be UNLOCKED" was considered, not "what must STILL LOOK locked after its previous greying source (the container) is unlocked".
26. **An exception function that sets a class/state only ADDITIVELY (never takes it back when its own condition no longer applies) is almost always wrong across several recompute cycles.** An early `return` when the exception "is not needed" ("normal case, nothing to do") prevents exactly the withdrawal of the function's OWN earlier additions from a PREVIOUS call — they stay stuck while the normal tree pass in parallel (for elements it manages itself) independently makes its own, correct decision → double nesting per rule 14, but only visible at state transitions (empty the format list briefly and fill it again), not in the steady state — hence easy to miss. **Every exception function must clearly distinguish two cases for EVERY element it touches:** (a) elements that ONLY this function itself controls (no other node in the tree ever sets their class) — tag these with an own marker (e.g. a `data-ep-<name>-grey` attribute) and, on leaving the exception, take them back ONLY based on this own marker, never force `classList.remove`/`toggle(false)` wholesale. (b) elements that are ALSO managed by the normal tree pass (which runs BEFORE the exception function in EVERY cycle and sets its state freshly and explicitly) — here stay completely idle in the normal case (exception not active), force nothing, trust the tree. Found at `epApplyFavoritesPeopleFormatException` (Sessions 102–109): 255 rule-14 violations on every format-empty-then-full-again transition because the function grew additively (Session 108: 10 subs' header/body; Session 109: 4 more fields) without ever getting a symmetric withdrawal.

27. **One-line descriptions (Session 117, TOP-PRIORITY user rule).** Every field description (`.epDesc`, `.epDescInline`) is exactly one line at the reference width 1920 px with Jellyfin's Noto Sans 10.5 px — never a wrap. Writing guideline: **max 105 characters** (the 804 px column fits ~108 average characters, nested subs have 794 px). Too long → shorten without changing the meaning; never let it wrap. Options are named in dropdown order. Tab intro paragraphs (`.epTabDescArea`, `white-space:normal`) are the only multi-line texts. Enforced by `tests/test_description_length.py` (renders the preview at 1920 px, fails on any wrap or any text over 105 chars) as a gate in `run_checks.py`. Measured, not guessed: 292 descriptions checked live in the user's Chrome, 13 wrapped, all shortened.

## Part B — Found contradiction (example of how this is supposed to work here)

**W1 — Rule 1 vs. the tab-button function (Session 24/26):**
Rule 1 says "never upwards". The function "tab button greys when all child functions in the tab are ineffective" is by definition a bottom-up effect (children influence the state of their own tab button).

**Resolution, not contradiction — but only because deliberately kept narrow:** this one exception affects **exclusively the tab button label**, never the tab PAGE itself (`epTabLocked` stays strictly rule-1-compliant, reacts only to General). Deadlock is structurally excluded: General sits on a DIFFERENT tab, is never affected by this bottom-up effect itself, and therefore always remains the escape route. **If this exception is ever extended** (e.g. to the page itself, or to deeper nesting levels than "direct children"), that must first be entered here as a new, checked case — not simply implemented.

## Part B2 — Deliberately broken rule (Session 29/30, explicit user decision, refined in Session 30)

**Rule 2 ("greying never changes a stored value") no longer applies without restriction since Session 29.** On explicit request a targeted, documented mutation chain was introduced — Session 30 refined the uniform pattern behind it:

```
Detail AND Library both off
    →  Show on switches itself off (value mutation, Show on itself stays clickable)
    →  Detail/Library rows grey out (normal top-down, because Show on is now off)

All Show-on boxes of a feature off
    →  Enable switches itself off (value mutation, Enable itself stays clickable)
    →  Show-on row greys out (normal top-down, because Enable is now off)
```

**The pattern is identical on every level:** when a level becomes completely empty, the level above unticks itself automatically (mutation) — and because that level is now off, the level just left greys out (by the perfectly normal, unchanged top-down rule). The TRIGGERING level (Detail/Library, Show on) always stays clickable; only the greying it CAUSES affects the level it has just left.

**Why this is not a deadlock:** Enable (the top level) is greyed by NOTHING — it is always the escape route. Way back: re-check Enable by hand → Show-on row becomes normal again → re-check Show-on boxes by hand → Detail/Library rows become normal again → re-check Detail/Library by hand.

**Correction versus Session 29:** the exception introduced then ("Show on must never be greyed by Enable, only by Format") is **lifted**. `postercase_showon`/`keyart_showon`/`extraposterfeature_showon`/`extrakeyart_showon` are normal children of their respective Enable-gated parent node again, exactly as before Session 29.

Applies to: Detail/Library → ShowOn for all Detail/Library pairs (Animated Poster/Keyart, Postercase/Keyart/Extraposter/Extrakeyart, each Movies + TvShows, plus the Sets variants since Session 87). ShowOn → Enable for the pairs with an own sub-feature Enable that is distinguishable from the tab root switch (Postercase, Keyart, Extraposter, Extrakeyart, Backdrops and its sub-categories, Animated Poster/Keyart since Session 90). Characterart and Red Carpet have NO standalone sub-feature Enable — their root gate (`CharacterartEnabled`/`RedCarpetEnabled`) already IS the only Enable, a mutation onto it is not applicable. Systematically confirmed (Session 34): every ShowOn group in the whole plugin listed automatically and compared against every tab root gate — no further missing pairs. (Case had its own sub-Enable `CaseModCaseEnabled` at the time; it was removed as redundant in Session 37, see bug log.)

**The mutation deliberately runs one-way only** (never automatic re-checking) — a reset level stays reset until the user re-checks it.
